# Apply to roles

Fetch `workflow_check` with `inspect_tools` when validating saved-answer scope/date or form readback. Its inline `answer` and `form` schemas require sourced values, current page revisions and observed upload filenames; empty form observations need affirmative completeness evidence. Use `preview_packet` for source-hash drift before the separate begin boundary; neither check grants submit authority.

Read mentioned sources through read_record (batch related reads); generic guides/skills may return origin=toolkit. For native file tools, use the returned ledger/toolkit root for each source. Avoid repeatedly loading broad views or unrelated context.

Resolve the ledger root with bootstrap, then read its AGENTS.md, [operations guide](../../guides/career-operations.md), approved answers, profile decisions, current tracker entries and exact vacancy. Use find_application with a stage/query and paged results; read the generated pipeline only when a broad overview is needed. Start an apply run with explicit sources, a positive max_submissions and dry_run=false only when submitting is authorised. A limit caps submissions, not skipped discoveries. Saved/tracked-only scope stays within that list. For “all”, determine the finite eligible list and set its count; report exclusions without inventing extra preferences.

For a large batch, follow the configured ledger’s parallel workflow if it has one. Give each worker a distinct claimed vacancy and browser tab, share one bounded run, and group `check_duplicate` steps into their own `query_batch` calls. Resume or reconcile existing claims and attempts before assigning the same vacancy again.

Use available browser tools under the configured preference and user request. Before each role inspect exact and employer matches from `check_duplicate`, including cooldowns and unknown outcomes. Reuse recorded facts and draft narrative answers from evidence, including own-word prompts; don't ask for recorded answers again. Use settings.primary_cv returned by bootstrap unless a supported tailored variant materially helps. Save newly supplied defaults in the configured canonical answer sources with date, source, scope and limits.

Prepare the full form or first-contact email and save exact final answers/message. Read `settings.permissions`, `settings.daily_channel_limits`, and `settings.communication` (`tone`, `anti_patterns`, `sender_email`, `mirror_sent_style`) before drafting or preparing — avoid AI-cliché phrasing and match the candidate's own recent Sent voice when available. Pass the exact `channel` (`portal`, `direct_email`, or `recruiter_outreach`) to `prepare_application` so Job Harness atomically enforces both total and per-channel daily budgets at `begin_submission`. Call `prepare_application` with the matching vacancy record, source, CV and answers; it freezes the packet and reserves the attempt with one call. It returns frozen artifact paths; upload or attach those exact bytes. If answers, selected CV or destination change, cancel only an unstarted reservation and prepare with a new key; a begun attempt requires outcome reconciliation first. Reusing a key with changed source bytes is rejected. A packet hash does not establish factual accuracy; verify the claims and fit first.

Prepare/reserve only a complete form or verified official application email within user scope. For `direct_email`, verify the recipient address is explicitly published, prove zero prior Sent emails to that exact normalized address, and log any SMTP bounce (e.g. 550) immediately as `not_submitted` without retrying the bounced address. After any required action-time confirmations, call `begin_submission` separately; proceed with exactly one external Submit/Send only when ready_for_single_submit=true. Replayed results explicitly prohibit another Submit. For verification codes, follow the strict escalation ladder: (1) check live email first for an emailed security code or magic link triggered right after Submit and complete it once within the same attempt without blindly repeating Submit; (2) only as a last resort (e.g. SMS/app OTP the agent cannot read), ask the candidate asynchronously with an explicit absolute ISO cutoff (`settings.time_and_reminders.async_question_cutoff_minutes`) while continuing other independent roles in separate browser sessions; if unanswered by cutoff (`no_answer`), cancel an unstarted reservation or record `outcome_unknown` if already begun, close the tab, and notify the candidate. Respect `settings.browser_policy`: run at most `max_concurrent_applications` (typically 2–3) isolated named sessions at once, batch multi-field DOM actions per call, and retire/close every session immediately after `finish_submission` or `cancel_reservation`. Observe confirmation, preserve a screenshot or application confirmation email and call `finish_submission`. If interrupted after begin, inspect portal/email first; record outcome_unknown when unresolved. Never cancel or expire a begun attempt merely to retry. An unstarted reservation can be cancelled; a negative resolution requires real evidence that no submission occurred.

Route newly supplied candidate answers by scope so the agent learns without drift: role-specific exceptions stay in `applications/<slug>.md`; reusable defaults (work auth, notice period, travel, new project facts) go into `approved-answers.md` / `application-decisions.md` / `context/` with date, attribution, scope, and limits so the candidate is never asked twice.

Unknown personal declarations, mismatched eligibility and tool-required confirmations remain genuine exceptions. Existing user authority persists; don't add per-form approval gates. If a portal is blocked, preserve prepared work and continue other roles within scope. Keep requested external tracker/board stages aligned with verified outcomes and log changes. Finish with confirmed submissions, duplicates avoided, prepared exceptions and evidence links; follow the ledger's commit rule for the owned packets/records/log. No unsolicited recruiter outreach or offer acceptance.

In focused MCP, load named specialised schemas with inspect_tools and run them as batch steps. Use query_batch for related reads and execute_batch for ordered local updates; pipe prior result fields with $ref. Read the version 2 data/error/next envelope. Page until next_offset is null when claiming exhaustive coverage. Use plan_adapter and record_adapter_result for requested external board sync, with actual live observations. See the [tool contract](../../guides/job-harness-contract.md) when recovering or composing batches.
